# Agent VM

Виртуалка для LLM-агента на [microvm.nix](https://github.com/microvm-nix/microvm.nix).
Внутри агент может делать что угодно. Единственный сетевой интерфейс подключён
к отдельному network namespace на хосте; sing-box вне VM направляет выбранные
домены через прокси, остальные — напрямую. По умолчанию прямого uplink у namespace
нет; режим `lan` добавляет отдельный DHCP-адрес для входящих соединений.
`/nix/store` общий с хостом, сборки уходят в хостовый nix-daemon.

## Пользоваться

```sh
avm start            # поднять и дождаться загрузки
avm ssh              # зайти внутрь
avm ssh htop         # выполнить команду и выйти
avm stop             # погасить
```

Ещё:

```sh
avm status           # запущена или нет
avm restart
avm reload           # применить mounts без перезапуска
avm logs             # консоль VM
avm logs proxy       # лог внешнего sing-box
```

Есть таб-комплит: `avm <Tab>`. Пароль не спрашивает.

Сама по себе виртуалка не стартует — только руками.

В госте `nix-shell` использует `nixpkgs` из закреплённого input flake через
`nix.settings.nix-path`, без channels. Для `ping`: `nix-shell -p iputils`.
Изменение этого параметра требует обновления сборки VM; `avm reload` его не применяет.

## Настроить

Машинные настройки лежат в `~/agent-vm/config.yml`, вне репозитория и
`/nix/store`. Команда создаст пустой конфиг с правами `0600` и откроет его в
`$VISUAL`, `$EDITOR` или `vi`:

```sh
avm config
```

Путь можно получить без открытия редактора: `avm config path`.

Пример полного конфига:

```yaml
proxy:
  - "*.openai.com"
  - "*.anthropic.com"
outbound:
  type: socks
  server: 10.9.8.7
  server_port: 1080
  username: sekai
  password: "hunter2"
mounts:
  - host: /home/spliterash/projects
    guest: /projects
  - host: /home/spliterash/.gitconfig
    guest: /home/spliterash/.gitconfig
    readOnly: true
  - "/home/spliterash/.ssh/known_hosts:/home/spliterash/.ssh/known_hosts:ro"
```

`*.` в `proxy` означает сам домен и любые поддомены. Что не попало в список,
идёт напрямую. При пустом списке `outbound` можно оставить `null`.
Значения с ведущим `*` нужно заключать в кавычки. YAML читает готовый `yq`;
конфиг должен содержать один документ-объект.

`outbound` — любой outbound из
[документации sing-box](https://sing-box.sagernet.org/configuration/outbound/).
Поле `tag` писать не надо, оно проставляется автоматически.

Kill switch находится вне VM. По умолчанию namespace содержит только гостевой
TAP и TUN sing-box, без user-сети qemu, bridge, veth и прямого uplink.
Правила nftables отправляют новые исходящие соединения только через TUN.
Недоступен outbound — домены из списка не открываются, остальные продолжают
работать. Остановился sing-box или исчез TUN — новый исходящий трафик блокируется.
В режиме `lan` входящие LAN-соединения и ответы на них продолжают работать;
это не запасной путь в интернет. SSH через vsock остаётся доступен.
Гостевой root не может снять эти правила.
Sing-box — дочерний процесс `microvm@agent`, отдельного proxy-сервиса нет.

`domain_suffix` покрывает сам домен и поддомены любой глубины, но не похожие
имена вроде `notifconfig.me` или `ifconfig.me.example.org`.

Граница защиты: хостовый nix-daemon намеренно сохранён. Сборки и загрузки,
переданные ему через vsock, используют сеть хоста, обходя эту политику.
Доменные правила также не являются запретом произвольных туннелей через
разрешённые direct-адреса. Проброшенные каталоги и SSH-ключи остаются отдельным
доверием гостю; это не полная изоляция от хоста.

Путь `host` в `mounts` может быть каталогом или отдельным файлом, тип определяется
автоматически. Оба пути должны быть абсолютными; `host` должен существовать на
хосте до старта VM, а `guest` будет создан внутри неё. Для объектной записи
`readOnly: true` включает монтирование только для чтения. По умолчанию используется
режим чтения и записи.

Есть короткий Docker-подобный формат `host:guest[:ro|rw]`:

```yaml
mounts:
  - "/home/spliterash/projects:/projects"
  - "/home/spliterash/.gitconfig:/home/spliterash/.gitconfig:ro"
```

Объектные и короткие записи можно смешивать. Если запись одна, массив можно
опустить и передать объект или строку напрямую. Все монтирования bind-ятся на
хосте в `/run/avm/shares/<sha256 пути>[:ro]` и уходят в VM одной virtiofs-шарой; для файла
соседние файлы из его каталога гостю не видны. Всё, что гость создаёт в шарах
(в том числе от root), на хосте принадлежит пользователю.

Изменения `mounts` применяются на живой VM через `avm reload`: новые записи
монтируются, удалённые снимаются, остальные не трогаются. Прокси, outbound и
`network` применяются только через `avm restart`. После первоначального обновления
хостовой конфигурации для переключения режима пересборка системы не нужна.

Снятие через `reload` ленивое: процессы гостя, у которых уже открыт файл или
каталог в снятой шаре, сохраняют к нему доступ до закрытия. Нужен гарантированный
отзыв доступа — `avm restart`.

Проверка всех настроенных монтирований (включая запрет записи в `readOnly`),
GPG-подписи, формата самостоятельных QCOW2-образов, HTTP/HTTPS, прокси для
`ifconfig.me`/`www.ifconfig.me` и прямого выхода через ipify, AWS checkip и
icanhazip: `python3 agent/check.py` из репозитория при запущенной VM.
В `proxy` должен присутствовать `ifconfig.me` или `*.ifconfig.me`.

Только монтирования: `python3 -c 'from agent.check import check_mounts; check_mounts()'`.
`avm start` и `avm restart` завершаются с ошибкой, если гостевые монтирования не поднялись.

## Адрес в локальной сети

Хост остаётся на `192.168.0.50`; его интерфейс не переносится в bridge.
В `~/agent-vm/config.yml` можно включить отдельный LAN-адрес:

```yaml
network:
  mode: lan
  interface: enp7s0
```

На роутере закрепить **`192.168.0.25` за MAC `02:00:00:00:42:25`** (имя DHCP-клиента — `agent`).
До закрепления роутер выдаёт любой свободный адрес; после закрепления нужен
`avm restart`, чтобы запросить новую аренду. Адрес получает DHCP-клиент в namespace AVM.
При отсутствии DHCP-ответа VM не запускается; статический адрес или обход
sing-box автоматически не включаются.
Нужен Ethernet-интерфейс в сети роутера; Wi-Fi для этой схемы не подходит.

Это macvlan + DNAT, а не смена гостевого IP: внутри VM остаётся `172.30.42.2`.
Входящие IPv4-соединения на LAN-адрес направляются в гостя с сохранением IP клиента;
ответы выходят с `192.168.0.25`. Новые исходящие соединения гостя по-прежнему идут
через sing-box и прежние `proxy`/`outbound`; прямые исходящие соединения sing-box
используют IP хоста, а не `192.168.0.25`. IPv6 на LAN-интерфейсе отключён.
Это не L2-мост для multicast/broadcast discovery.

Сервисы должны слушать `0.0.0.0` или гостевой адрес, не `192.168.0.25`.
Гостевой firewall отключён: в режиме `lan` все слушающие гостевые порты доступны
с хоста и из сети роутера без отдельного открытия. Собственная аутентификация
сервисов по-прежнему нужна. Внешний kill switch в namespace AVM остаётся включённым
и блокирует новые исходящие соединения в обход sing-box.

С самого хоста приложения доступны по тому же LAN-адресу, например
`http://192.168.0.25:80`, без SSH-туннеля. AVM автоматически создаёт служебную
veth-пару и маршрут `/32` к текущему DHCP-адресу; дополнительный адрес в сети
роутера не нужен. При продлении аренды маршрут обновляется, при остановке VM
служебный интерфейс и маршрут удаляются. Ответы на входящие соединения
разрешены, новые исходящие соединения гостя через эту пару — нет.

При нормальной остановке (`avm stop` или выключение гостя) DHCP-клиент отправляет
роутеру DHCPRELEASE до удаления LAN-интерфейса. Аренда освобождается; запись в
истории клиентов или DHCP-резервациях может остаться. Метка активности в админке
роутера может обновляться с задержкой из-за его кэша/ARP, это не означает, что VM работает.

Текущий адрес до закрепления можно узнать на хосте:

```sh
ip -4 route show dev avm0 proto static
```

Вернуть прежний режим:

```yaml
network:
  mode: isolated
```

Удаление `network` также включает `isolated`. Изменение конфига применяется
при следующем `avm restart`; `avm reload` меняет только монтирования.

Первоначальное применение изменений репозитория — **только когда можно остановить VM**:

```sh
avm stop
nh os switch
avm start
```

Изолированная проверка без остановки рабочей VM: `python3 agent/check-network.py`.
Она собирает сетевой launcher из закреплённого nixpkgs и запускает его в новых
user/mount/network namespaces с виртуальным DHCP-роутером. Гостевой TAP заменён
на veth только в проверочной копии launcher; реальные nftables, DHCP и sing-box
не подменяются. Проверяются оба режима, DHCP-резервация `.25`, входящий HTTP с
хоста и LAN, исходящий HTTP через sing-box и отсутствие прямой утечки на LAN
или хост после остановки проверочного sing-box. Входящие соединения с хоста и
LAN при этом остаются доступны. Также проверяется удаление служебного маршрута
и интерфейса и освобождение DHCP-аренды у проверочного роутера после остановки VM.

## Git и подпись GPG

VM использует те же настройки `common/home/git.nix`, что и хост: имя, email,
ключ по email и автоматическую подпись коммитов и тегов. При старте хост
экспортирует публичные ключи в `/run/avm/host/gpg-public-keys`, Home Manager
импортирует их в гостя. После добавления ключей на хосте нужен новый старт VM.

Приватные ключи не копируются и не монтируются. Гостевой GPG обращается через
vsock к ограниченному `gpg-agent-extra.socket` хоста; пароль запрашивает
хостовый pinentry. Хостовый мост принимает только CID этой VM (`4242`), а не
соединения других пользователей хоста или других VM. Требуется запущенный
пользовательский systemd хоста. Гостю доверяется использование ключей для
подписи и расшифровки; extra-сокет не ограничивает его только Git-коммитами.

Применение конфигурации — **когда можно остановить VM**:

```sh
avm stop
nh os switch
systemctl --user stop gpg-agent.service
systemctl --user start gpg-agent-extra.socket avm-gpg-agent.socket
avm start
```

Хостовый `gpg-agent.service` требует extra-сокет и запускается после него:
обычный GPG-запрос на хосте не может поднять агент без сокета для VM.
Перезапуск хостового gpg-agent нужен при первом добавлении extra-сокета к уже
работающему агенту. `avm reload` эти изменения не применяет.

Если меняется только зависимость хостового агента, VM останавливать не нужно.
После применения конфигурации достаточно команд `systemctl --user stop gpg-agent.service`
и `systemctl --user start avm-gpg-agent.socket`.

Проверка из репозитория: `python3 -c 'from agent.check import check_signing; check_signing()'`.
Она проверяет отказ подключения с хоста, совпадение Git identity и подпись
временного коммита внутри VM; может появиться запрос пароля на хосте.

## Как устроено

| | |
|---|---|
| `/nix/store` | virtiofs от хоста, read-only; virtiofsd под root ссылается на inode через file handles, а не держит по открытому fd на каждый |
| nix | `NIX_REMOTE=daemon`, сокет прокинут в хостовый nix-daemon через vsock |
| ssh | управление через vsock (`ssh agent`); при `lan` также доступен TCP/22, только ключевая аутентификация |
| сеть | TAP в отдельном namespace; LAN-режим добавляет macvlan для роутера и служебный veth для доступа с хоста; новые исходящие соединения идут только через TUN |
| прокси | sing-box — дочерний процесс AVM; TUN создаётся только в namespace, сеть хоста не перенастраивается |

Юниты на хосте: `microvm@agent`, `microvm-virtiofsd@agent`, `avm-prepare`
(читает `config.yml`, готовит шары) и `avm-nix-daemon.socket`.
Sing-box запускается и останавливается вместе с VM; при пустом `proxy`
он направляет весь трафик напрямую через тот же изолированный шлюз.

## Файлы

| | |
|---|---|
| `~/agent-vm/config.yml` | локальные proxy/outbound/mounts/network, не попадает в git и store |
| `~/agent-vm/ssh/` | ключ, которым `avm ssh` заходит внутрь |
| `~/agent-vm/disks/docker.qcow2` | образы и контейнеры docker |
| `~/agent-vm/disks/root.qcow2` | корень VM (home, кэши, всё вне шар) |
| `/var/lib/microvms/agent/` | ссылки на сборку, управляющие сокеты и служебные файлы microvm, без дисков |

Ключ генерится сам при первом `avm start`. Потерялся — удали `~/agent-vm/ssh`
и запусти снова.
Перед стартом `disks/` bind-монтируется в `/run/avm/disks`, чтобы QEMU под
пользователем `microvm` не требовал доступа к закрытому домашнему каталогу.
При остановке bind снимается; образы остаются в `~/agent-vm/disks`.

Используется QCOW2 без backing-файлов: сами файлы образов растут по мере
записи данных, а не имеют сразу длину виртуального диска. Ёмкость внутри VM
по умолчанию — 8 ГиБ для корня и 32 ГиБ для Docker. Отсутствующие образы
создаются и форматируются перед запуском; существующие не пересоздаются.

## Что переживает перезапуск

| | |
|---|---|
| Образы и контейнеры docker | да |
| Всё остальное внутри VM | да, корень хранится в `root.qcow2` |
| Скачанное через `nix-shell` / `nix build` | да, попадает в store хоста |

Файлы внутри `mounts` живут на хосте, их VM не трогает.

Docker начать с нуля: `avm stop && sudo rm ~/agent-vm/disks/docker.qcow2`,
корень — то же самое с `root.qcow2`. Удалённый образ создастся заново при старте.
